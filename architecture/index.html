Get Started

The architecture of the system may seem complex at first, by looking at the code, but trust me, it is simple.

Simply put - this system (the intranet, and public website) are all running on a serverless architecture, so:

  • AWS Lambda runs the code in nodejs v22.x
  • AWS DynamoDB is the database - as of writing, this includes users who have logged in, and student groups
  • AWS S3 is also storage - but it holds other binaries such as documents, avatars, and even data such as the hashed list of CIS codes
  • AWS SES - send emails

Everything is in eu-west-2 (London) region. Make sure anything new you ever do is also in eu-west-2 (London) because of GDPR reasons.

If you need to change this manual however, it is simply GitHub pages. The repository is at https://github.com/josephinebutlerjcr/manuals.

Want to unpick my entire thought process? Visit the Q&As at /architecture/qanda.html

AWS Lambda

Simply put, you do not need to touch the Amazon AWS Lambda functions, unless the version is deprecated. If so, just google how to change the versions around (I am not gatekeeping this from you - AWS keep changing around their UI, and by the time you need to change it, it will probably change - it is annoying).

But, there are two functions:

  • internal-website
  • public-website

There are also two repositories:

  • https://github.com/josephinebutlerjcr/intranet
  • https://github.com/josephinebutlerjcr/public-website

Coincidence? I think not! They correlate - and any commits to the main branch will directly update the Lambda functions.

This is why you should NEVER commit directly to the main branch - make a separate branch, do stuff, and merge it. If you are a volunteer, this is where the webmaster can check your code is in order.

More on the code structure here.

AWS DynamoDB

As of writing, there are two databases.

users

This database ("users") contains the details of each individual - they must be logged onto the system for a record to be generated.
Key Data Type Remarks
cis String Partition Key. CIS code of user
generated Integer Unix time of the first time the account was generated. This is the number of seconds from 01/01/1970 00:00 UTC+0
login Object An object of: attempts (integer) (number of consecutive failed sign in attempts), attemptsOnCode (integer) (number of consecutive failed sign in attempts on the code), code (string) (6 digit login code), and generated (integer) (unix time of when the code was generated - may be -1 instead to denote expiry)
membership String Currently not in use - just write default "N/R"
name String Name of the user - they can write it in / edit
privilege String Takes on: general, exec, chair, admin - different access levels in ascending order of authority
token Object The current token they are signed in on. An object of: exp (integer) (expiry of token in unix time - may be -1 to denote the user has signed out manually), and key (string) (32 digit hexadecimal token)
newUser Boolean A flag to denote if the person is new / not properly logged in yet - perhaps due to them signing in but not entering the code in their emails, or the account being force made as they are in the exec. This field is optional - if blank, assumed false.

groups

This database ("groups") contains the details of each JCR student group. I call it "student group" instead of "SSC" (sport, society and committees), just because screw having yet another abbreviation.

Now, the id was a slug generated from the original category and name, where the category got truncated to the first 3 letters, and then names and spaces are in lower case and have a dash (-) in lieu of a space.

For example, the Netball group (sport) would become spo-netball. Likewise, the technical committee would be com-technical-committee.

Key Data Type Remarks
id String Partition Key. The slug I just told you about.
admins Object Unix time of the first time the account was generated. This is the number of seconds from 01/01/1970 00:00 UTC+0
avatar Boolean Flags whether or not an avatar for the student group exists.
awards List of Strings List of any awards the society has - can be an empty list.
category String Self-explanatory. Takes on: sport, committee, society
description String Self-explanatory.
events List of Objects Currently a blank list for all societies because I have not implemented a DU-Pulse style thing - although their website doesn't work for societies! Ideal for calendars.
name String The name of the society.
socials Object Can be blank. All values are strings. Keys: "instagram" (Instagram username without handle e.g. @butler.slackline to butler.slackline), "whatsapp" is the WhatsApp invite link without the rest of the URL e.g https://chat.whatsapp.com/123/ --> 123

AWS S3

There are two buckets:

  • butler-jcr
  • butler-jcr-public

The key difference is, anything in butler-jcr-public can be viewed anywhere on the internet, without needing a presigned key, in the form butler-jcr-public.s3.eu-west-2.amazonaws.com/path/to/file.ext, for example https://butler-jcr-public.s3.eu-west-2.amazonaws.com/avatars/0.jpg.

butler-jcr

This includes anything not available to the public - at least not without a presigned URL. In this I have saved:

  • Executive data - roll mapping, and individual biographies - both as a json
  • Family data - currently empty as I have done nout here but the intention was a bunch of jsons
  • List of hashed CIS codes - its in the root as "hashed_db.txt" - you must change the contents of this file with anything new sent from the FACSO. This file is important as it includes all members in the college, and is used to ensure first-time sign ons are only for this college. At the beginning of the year, please get your FACSO/President to follow the instructions in /admin/encrypt.html. Please consult your handover for the pepper.
  • Audit logs - e.g. for uploads and changes to data - you must keep some sort of log ideally of stuff.

butler-jcr-public

Now this includes stuff you would not mind being seen by the public. Usually, the content for the public website e.g. images should be uploaded here and then you link to these, but it also includes data accessible in the intranet. Stuff here include:

  • Avatars - for both student groups, and exec members (for the latter, only the photos of the pres/FACSO is displayed on the public website)
  • Democracy documents
  • Policies and governance documents
  • Other public facing websire related uploads (done manually) - assets (e.g. logos), photos of limited events, and freshers week stuff.
